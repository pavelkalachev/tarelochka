# 012. Инструмент миграций схемы

Срез: Данные

Зависит от: 008

## Зачем

Схема должна накатываться одинаково локально и на сервере.

## Готово, когда

`make migrate` создаёт служебную таблицу `schema_migrations`. Повторный `make migrate` ничего не меняет. `make migrate-down` откатывает одну последнюю миграцию. `make migrate-status` печатает её номер.

## Шаги

1. Вызывать [golang-migrate](https://github.com/golang-migrate/migrate) v4.20.1 только из `Makefile`. Отдельную команду в README не добавлять. Сборка с тегом `postgres`, иначе драйвер базы в бинарник не попадает.
2. Каталог `migrations/`. Первая миграция — пустая пара `000001_init.up.sql` и `000001_init.down.sql`. Дальше у каждого изменения свои `.up.sql` и `.down.sql` с тем же номером.
3. `make migrate` читает `.env` и вызывает `migrate -path migrations -database "$$DATABASE_URL" up`. `make migrate-down` передаёт `down 1`: без числа инструмент откатил бы все миграции. `make migrate-status` вызывает `version`.
4. В локальном `DATABASE_URL` нужен `sslmode=disable`. Схема `postgres://`.
5. Схема только из этих SQL-файлов. Код приложения при старте таблицы не создаёт и не меняет. Docker их тоже не создаёт: ни init-скрипт образа, ни entrypoint.
6. Если миграция оборвалась, база помечается dirty и следующий `up` не идёт. Сначала починить SQL, затем `migrate force` на последнюю удачную версию и снова `make migrate`.

## Проверить

Два подряд `make migrate` завершаются без ошибки.
